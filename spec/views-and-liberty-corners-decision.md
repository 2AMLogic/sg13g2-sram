# Decision record: Verilog and CDL are target views; Liberty is delivered at all 45 corners

**Status**: Proposed, 2026-10-29 (not self-ratified)
**Resolves**: #75, market-key findings F4 and F5 on `spec/sram.md` @ `2597199`
(ratification review, #37)
**Origin**: `gf180-sram` `spec/sram.md` @ `d0bacc0` (Views row inherited as
CDL / Verilog stretch; this record departs from it for Verilog and CDL)

## Question

1. `spec/sram.md` lists CDL and Verilog only as stretch views, while the
   comparison macro ships both. Should they be target views?
2. The spec runs 45 corners but does not say how many the delivered Liberty
   carries. The comparison macro ships 3. How many do we deliver, and how
   are they packaged?

## Answer

1. **Verilog and CDL move from stretch to target.** The Views row becomes
   target: GDS, LEF, Liberty, CDL, Verilog, all generated by this repo's own
   flow. No stretch views remain.
2. **The delivered Liberty carries all 45 corners**, packaged as one Liberty
   file per corner, each named for its process, temperature and voltage. No
   subset is chosen here. Whether the flow can emit this is an open item
   (below), not an assumption.

## Rationale

### Views

1. The comparison macro's directory ships `cdl/ doc/ gds/ lef/ lib/ verilog/`
   (market-key sources table, fetched 2026-10-29; not re-fetched for this
   record). A buyer integrating the block needs a simulation model and a
   netlist; a target set without them is narrower than what the foundry
   macro hands over.
2. CDL is the LVS netlist form. The flow already needs a netlist of the
   macro for macro-level LVS, so CDL is a byproduct of work already in
   scope, not a new measurement.
3. A Verilog model is behavioral. It needs no new characterization and no
   corner data: it encodes the 1RW synchronous interface already fixed in
   `spec/sram.md` § Ports.
4. **Departure from the origin.** `gf180-sram` kept CDL and Verilog as
   stretch. This is recorded as a departure, made because the comparison
   macro for this PDK ships both and the origin had no such comparison
   point to match. Promotion to target does not weaken any ratified margin
   or signoff row.

### Liberty corners

1. The corner matrix is already run in full (5 × 3 × 3 = 45, no pruning)
   and access time is recorded at every corner (`spec/sram.md` §
   Characterization). The timing data for 45 Liberty files therefore exists
   once characterization runs; delivering fewer would discard it.
2. The comparison macro ships 3 corners (`fast_1p32V_m55C`,
   `typ_1p20V_25C`, `slow_1p08V_125C`), at diagonal points and with a
   −55 °C cold corner. Matching its count would drop the skew corners
   (`mos_sf`, `mos_fs`) that the spec adds on purpose, and 3 diagonal
   points cannot be reconciled with a matrix whose cold point is −40 °C.
3. One file per corner follows the comparison macro's packaging (one `.lib`
   per corner), so a buyer's flow loads them the same way.

## Open, verify at first run

- **Multi-corner Liberty emission is not traced.** It is not known whether
  the klt Liberty generation can emit more than one corner per run, or
  emit one file per corner from a single request. First run must record
  which, and the command used. If it cannot, that is a klayout-tools
  friction issue, filed there as a generic tool gap.
- If emitting 45 proves impractical, delivering a named subset needs a new
  decision record that names the subset and the reason. It is not a silent
  reduction.
- Verilog and CDL generation by the flow is likewise untraced. The first
  run records how each is produced and whether CDL matches the LVS netlist.
- Whether Liberty, Verilog and CDL generation run on the deck at this
  macro scale is itself part of the tool surface under test.

## What this record changes

`spec/sram.md`: the Views row (CDL and Verilog become target, stretch
becomes none), the Deliverables section (names the views and the 45-corner
Liberty), and the Depends-on header. No other row changes. Status stays
Proposed.
