## Organization: 1 kB, 256 × 32, fixed instance

Inherited. The shipped `RM_IHPSG13_1P_256x32_c2_bm_bist` has the same
organization and is the comparison point. A parameterized generator is a
stretch, after the fixed instance is DRC/LVS clean and characterized.
Free SRAM generators are references: cite, do not reimplement.

## Ports: 1RW, with the origin's pin interface

**Target 1RW; stretch 1RW1R.** Inherited.

Pin interface: keep the origin's (`A[n]`, `CEN`, `CLK`, `D[n]`, `Q[n]`,
`GWEN`, `WEN`), adapted to 8 address bits and 32 data bits. There is no
reason found for it to differ on this PDK. The shipped macro's interface
differs (`A_ADDR[7:0]`, `A_DIN[31:0]`, `A_DOUT[31:0]`, `A_BM[31:0]` bit
mask, `A_MEN`/`A_REN`/`A_WEN`, `A_CLK`, a `*_BIST_*` mirror, `A_DLY` tied
to 1) because it carries BIST and a per-bit mask; those are foundry
integration features, not a template. They are not required here.

## Supply and rails

**Target: 1.2 V ±10%: 1.08 V, 1.20 V, 1.32 V.** Re-derived: SG13G2 core
devices are 1.2 V (the origin ran 3.3 V). Only the low-voltage models are
in scope; `cornerMOSlv.lib` is the corner file, `cornerMOShv.lib` is not
used.

**Rail sharing: open.** The shipped macro has separate `VDD` (support logic)
and `VDDARRAY` (array) supplies. Whether this macro does too is a design
choice that depends on write margin and read SNM headroom, which cannot be
measured before the bitcell is characterized. **Target: one rail** (as in the
origin). **Stretch: a separate array rail.** Revisit by decision record if
the bitcell characterization shows a separate rail is needed to close
margins. Owner: the bitcell characterization issue.

## Deliverables: GDS, LEF, Liberty

Inherited. All three are generated by this repo's own flow, not consumed
from the foundry macro. This is the tool surface under test.

## Characterization

### Block kind

**Analog**, inherited from `gf180-sram` `spec/block-kind-decision.md`
(scope: custom bitcell/array and PVT characterization; future digital
periphery is a separate declaration).

### What must be measured

All inherited, at every corner, on the 256 × 32 array or a representative
column where a full-array simulation is impractical. Each is a recorded
margin, not a pass/fail:

- **Read SNM**: minimum butterfly-curve square side, bit lines precharged,
  wordline asserted, cell holding both values. Strictly positive.
- **Hold SNM**: same measurement in standby. Strictly positive.
- **Write margin**: minimum bit-line / write-driver drive that flips the
  cell within a fixed **1 ns** write pulse (`spec/write-pulse-width-decision.md`).
  Strictly positive. No independent macro timing target is ratified.
- **Access time**: clock edge to valid output, and write completion, per
  corner. Feeds the Liberty tables. Recorded at every corner; the typical
  corner (`mos_tt`, 25 °C, 1.20 V) is proposed to pass at clock-to-Q no worse
  than the comp's 3.05 ns (`spec/access-time-target-decision.md`, Proposed,
  not ratified; until it is, no pass threshold applies).

A corner passes only when read SNM, hold SNM and write margin are strictly
positive and access time is recorded. The proposed typical-corner access-time
threshold (`spec/access-time-target-decision.md`, Proposed) is not in force
until ratified.

### Statistical treatment

Inherited. Read SNM, hold SNM and write margin are mismatch-driven. Each
needs Monte Carlo evidence (recorded seed, sample count, deterministic
negative control, `klt yield` report) **combined with, never replacing**,
the corner matrix. Graded on Cpk, sigma-to-spec and the exact
empirical-yield lower bound, each with a confidence interval. **No numeric
`target_yield`.** Access time is not classified as statistical.

Re-derive note: SG13G2's models carry their own mismatch parameters. Which
ones the Monte Carlo draws is decided when the harness is run on the OSDI
models (#4, #5), and is recorded as a divergence if it differs from the
origin.

### Corner set

| Axis | Points |
|---|---|
| Process | `mos_tt`, `mos_ss`, `mos_ff`, `mos_sf`, `mos_fs` (the PDK's MOS corner set in `libs.tech/ngspice/models/cornerMOSlv.lib`) |
| Temperature | −40 °C, 25 °C, 125 °C |
| Voltage | 1.08 V, 1.20 V, 1.32 V |

**The full cross is run: 5 × 3 × 3 = 45 corners.** No pruning. The
skew corners (`mos_sf`, `mos_fs`) matter for SRAM because read stability and
write margin move in opposite directions across the skew. The origin ran
three process corners (3 × 3 × 3 = 27); the two skew corners are the
addition. All corners are reported under `sim/`'s append-only evidence
convention.

The three process-corner names above were confirmed present in
`cornerMOSlv.lib` (`.LIB mos_tt`, `mos_ss`, `mos_ff`, `mos_sf`, `mos_fs`)
on 2026-10-17.

### Signoff definition

The macro is functional across PVT once DRC and LVS are clean on the full
array and every one of the 45 corners has a strictly positive read SNM, hold
SNM and write margin, plus a recorded access time (and, if
`spec/access-time-target-decision.md` is ratified, the typical-corner access
time within its threshold). A corner that cannot be
closed is recorded as an open result, not dropped.

Liberty corners, the only three shipped:

| Name | Voltage | Temperature |
|---|---|---|
| `fast_1p32V_m55C` | 1.32 V | **−55 °C** |

The timing figures are from the first table entry of the `rising_edge` arc
for bit 0; they are a reference scale, not a full characterization.

## Deck acceptance

"Clean" means: zero violations from `klt drc` against klt's SG13G2 deck on
the bitcell, an abutment tile and the full array, and `klt lvs` clean
against the schematic netlist on the full array. This is stated here and
**not yet checked**: the deck has not been run on anything in this repo.
As of klt 0.7.1.dev1743+g7ee09483b748, `klt deck info --deck sg13g2` reports
deck content hash `sha256:08dbffe2…ec01c`, `released: False`, and device
classes `nfet, pfet, cap_cmim, rfcmim, cap_cmomi, cap_cmomf, resistor,
dantenna, dpantenna`. The deck is therefore unreleased; the hash is
recorded with every DRC/LVS result.

Array-relevant rules the deck is not known to check yet (to be established at
first run, not assumed):

- Whatever the `SRAM.drawing` (25/0) marker relaxes in the PDK's native
  rules. This repo's cell claims no relaxation (as the origin's did not)
  until a rule survey reads what the marker permits.
- Density rules at the 8,192-cell array scale, antenna, and latch-up
  (well/substrate strap spacing).
- Whether the deck's native-engine run and `klt`'s curated deck agree (the
  origin found the curated deck missed five rule families on the native run).

Each gap found is filed at `2AMLogic/klayout-tools` per the friction
protocol, described generically.
